# 压缩高可用方案（plan）

> 目标：**压缩永远不因"发不出去"而失败**。会话多大、切到多小的模型，都必须能压回来。

## 0. 现状与失败模式

`summarize()` 当前的输入构造（`lib/index.js:293`）：

```js
function summarizationInput(input, agent) {
	const messages = fullConversationMessages(agent?.session);
	return messages === undefined ? input : { ...input, messages };
}
```

**无条件全量重放**。`fullConversationMessages` 把 `session.surface.nodes` 里每个节点都投影成消息。

失败链（Win11 实测）：

```
会话 21.7 万 token（窗口 1M）
  → 上游按自己的口径拒（context_length_exceeded）
  → 触发压缩
  → 压缩要发全部 21.7 万 + 指令
  → 同样被拒
  → 压缩失败，会话不可恢复
```

**根本问题：压缩请求本身没有大小上限。** 它是唯一能救会话的操作，却和它要救的东西一样大。

| 场景 | 现在 | 应该 |
|:--|:--|:--|
| 会话 < 窗口 | 全量重放，缓存命中 ✅ | 不变 |
| 会话 > 窗口 | 失败 ❌ | 必须能压 |
| 1M 会话切到 256K 模型 | 失败 ❌ | 分批压回来 |

## 1. 设计原则

1. **压缩是不可失败的操作。** 它是所有其他失败模式的恢复手段；它自己失败就没有兜底了。
2. **默认路径不变。** 正常情况（会话 < 窗口）保持全量重放的缓存命中优势，不能为了救边缘情况拖慢日常。
3. **逐级降级，每级都不需要用户干预。**
4. **每一级失败都要说清楚降到了哪一级**，不能静默。

## 2. 分级策略（在 `summarize()` 内实现）

设 `W` = 目标模型的 contextWindow，`B` = `floor(W × 0.8)`（预算，留 20% 给输出与指令）。

```
① 全量重放        估算 ≤ B ?  → 用全量           （缓存命中，Mac 现行路径）
② 区域重放        父类 input ≤ B ? → 用父类 input  （只发被压那段）
③ 分批压缩        以上都不行    → 见 §3
④ 离线裁剪兜底    分批仍失败    → 见 §4
```

**估算 token 的方式**：不引入新依赖。用 `ctx.tokenMeter.measure()` 对该消息列表构造一个最小会话影子测一次；若接口不支持任意消息列表，退化为**字符数 / 3** 的保守估算（对中英混排偏保守，宁可低估预算）。

> 待确认：`tokenMeter.measure` 只接受 session。若不能测任意列表，②③④ 全部基于字符估算。

## 3. 分批压缩（核心）

会话超出窗口时，把历史切成若干批，**每批都带上前一批的摘要**，一次压一段：

```
batch 1: [最早的节点 …塞满 B]                     → S1
batch 2: [S1 作为一条 assistant/user 消息] + [后续节点…塞满 B] → S2
batch 3: [S2] + [后续…]                          → S3
…
直到覆盖完 → 最终摘要 Sn
```

- 每批的输出（摘要）远小于输入，所以 **Sn 一定装得下**。
- 信息不丢：后续批次能看到前面所有批次的浓缩。
- 代价：N 次 LLM 调用，9.7MB 的会话可能 5–10 次。

**必须实现的保护**：
- **批次数上限**（默认 12）。超限说明会话大到不可救，报错并建议开新会话，而不是无限循环烧钱。
- **每批之间检查 `signal.aborted`**，用户取消要立刻停。
- **进度可观测**：每批打一行 `[compaction] batch i/N tokens=… → …`。

## 4. 离线裁剪兜底

分批都不行（比如模型窗口太小，单批塞不下几条消息），放弃 LLM，直接改历史：

- 把超大的 `tool/result`（> `headChars`）替换为保留头尾 + `[N KB 已省略，命令：…]`。
- 连续相同的 tool 调用合并成一条。
- **不删除** user/assistant 消息（那是语义主干），只砍 tool 输出。

这一步不需要任何模型，**必然成功**。代价是丢细节。

## 6. 验收

- [ ] 全量能装下时行为**完全不变**（现有 201 个测试全绿）
- [ ] 会话 > 窗口时压缩成功（e2e `oversize`）
- [ ] 1M 会话切 256K 模型后能分批压回来（e2e `shrink`，用一个假 provider 先大后小）
- [ ] 批次数超限时报错明确，不静默
- [ ] 每一级降级都打一行诊断，能看出走的是哪条路
