# 压缩高可用方案

> 目标：**压缩永远不因"发不出去"而失败**。

## 0. 已解决：全量重放（2026-11-26）

`summarize()` 曾把整段对话重放，让摘要请求成为 live state 的精确 token-前缀延伸
（为了本地引擎的 `--prompt-cache` 命中）。**该机制已删除**，用官方的 region-only。

它不是"偶发过大"，而是**结构上必然失败**。Win11 会话实测（`session-91ac1b04`，
从未成功压缩过）：

| 请求体 | tokens |
|:--|--:|
| 全量重放（带 reasoning） | 2,182,311 |
| 全量重放（剥掉 reasoning） | 1,247,719 |
| 网关实际请求峰值 | **217,373** |
| 声明窗口 | 1,000,000 |

区别在于**正常请求只发当前窗口内的内容**，而全量重放试图把**累计历史**（1.25M）
全部塞进一次请求。剥掉 reasoning 只能从 2.2M 降到 1.25M —— 仍然超窗。

**结论：需要压缩的会话，恰好就是全量重放装不下的会话。** 用来救它的请求，正是
发不出去的那个。四次压缩全部 `context_length_exceeded`，会话永久不可恢复。

region-only 的区域由触发压缩的 gate 限定，**因此天然有界**。这是唯一正确的做法。

## 1. 剩余风险

回到 region-only 后，摘要请求体积 = 被压区间。该区间由 gate 选中，正常情况有界。
但仍有一种情况会超：

**1M 会话切到 256K 模型。** gate 按 256K 计算，选中区间相当大，摘要请求可能装不进
256K 窗口。

## 2. 保底方案（`lib/summarize-budget.js`，已写好 19 个测试）

显式给摘要请求设上限，超了就分级降级：

```
① region-only      父类 input 装得下  → 直接用        （默认路径）
② 分批压缩         装不下            → 切成 N 批，每批带前批摘要
③ 离线裁剪         分批仍不行        → 砍 tool 输出，不调模型
```

**分批的接续方式**：

```
batch 1: [最早的节点…塞满 80%]                → S1
batch 2: [S1] + [后续节点…塞满 80%]           → S2
batch 3: [S2] + [后续…]                       → S3
```

每批带上前一批摘要，信息不丢。批次数上限 12，超了就明说"开新会话"而不是无限烧钱。

**离线裁剪只动 tool 输出** —— 那是长会话的体积主体，也是唯一可重建的部分；
user/assistant 消息是语义主干，永不删除。
